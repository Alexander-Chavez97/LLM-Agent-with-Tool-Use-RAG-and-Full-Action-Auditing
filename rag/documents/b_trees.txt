B-Trees

A B-tree is a self-balancing tree data structure designed to keep data sorted while allowing searches, insertions, and deletions in logarithmic time, and it is the structure most relational databases use to implement indexes. Unlike a binary search tree, where each node has at most two children, a B-tree node can hold many keys and many children, which keeps the overall tree shallow even when it stores millions of entries.

This shallowness matters enormously in practice because it directly affects disk I/O. Reading from disk is orders of magnitude slower than reading from memory, and each disk read typically pulls in a fixed-size block. B-tree nodes are deliberately sized to match that block size, so a single disk read retrieves an entire node's worth of keys at once. A tree with a branching factor of several hundred can hold millions of records in only three or four levels, meaning a lookup touches disk only three or four times regardless of table size.

Insertions and deletions in a B-tree preserve a set of balance invariants: every leaf appears at the same depth, and every node (except possibly the root) stays within a defined range of how many keys it can hold. When a node would overflow past its maximum, it splits into two nodes and pushes a key up to its parent; when a node would underflow below its minimum, it borrows a key from a sibling or merges with one. These rebalancing operations are what keep the tree's height logarithmic no matter what order data is inserted in.

The distinction between a B-tree and the commonly used B+tree variant matters for databases specifically: in a B+tree, all actual data is stored in the leaf nodes, and internal nodes hold only routing keys, with leaves additionally linked together in a chain. That linked-leaf structure makes range queries -- "give me all rows between X and Y" -- efficient, since once the starting leaf is found, the rest of the range can be read by walking sequentially along the leaf chain rather than re-traversing the tree.
