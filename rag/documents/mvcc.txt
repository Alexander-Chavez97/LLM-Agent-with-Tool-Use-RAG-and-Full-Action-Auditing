Multi-Version Concurrency Control (MVCC)

Multi-version concurrency control is a technique databases use to allow multiple transactions to read and write data concurrently without blocking each other, by keeping multiple versions of a given row rather than overwriting data in place. When a transaction updates a row, instead of destructively modifying the existing row, the database creates a new version of that row tagged with information about when it became valid.

Under MVCC, a read operation does not need to acquire a lock on the data it is reading. Instead, each transaction sees a consistent "snapshot" of the database as it existed at some specific point in time -- typically the moment the transaction began. This means a long-running read transaction is never blocked by concurrent writes, and concurrent writes are never blocked by ongoing reads, which is a major improvement over older locking-based concurrency schemes where readers and writers could stall each other.

This approach is not free: keeping multiple versions of every row means storage grows until old, no-longer-visible versions are cleaned up. PostgreSQL, one of the most well known databases using MVCC, calls this cleanup process "vacuuming." If vacuuming falls behind -- for example due to a long-running transaction holding an old snapshot open -- old row versions can accumulate significantly, a condition informally called table bloat, which degrades both storage efficiency and query performance.

MVCC also changes what "consistency" means operationally: two concurrent transactions can each see a different, individually consistent snapshot of the same table at the same wall-clock time. Reconciling conflicting writes made under different snapshots is handled through mechanisms like write-write conflict detection, where a transaction attempting to update a row that has since been changed by another committed transaction is forced to retry or abort, depending on the isolation level in effect.
